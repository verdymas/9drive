# Preferences
- Treat credentials as highly sensitive: API tokens, secrets, HMAC signatures, signed URLs, cookies, auth headers must NEVER be committed to source, `.env`, fixtures, tests, or snapshots, and must never be printed/logged. Provide them only via environment variables or temporary shell env. Confidence: 1.0
- When logging or propagating errors, never echo the URL, headers, body, secret, or signature — surface only a safe reason code/hint. Confidence: 0.9
- Prefer backend/integration/API testing over browser automation — do NOT use Playwright or frontend E2E for backend integration tests. Use backend services, API requests, Cloudflare API, service classes, Docker, and backend logs. Confidence: 1.0
- In tests, reuse the real production classes and code paths (serializers, transports, drivers, services) rather than reimplementing logic independently in the test. Test what actually ships. Confidence: 0.95
- Prefer real end-to-end testing against real provisioned resources (real Worker, real upstream) over mocks alone. Confidence: 0.9
- Write contract/regression tests that guard against drift between two sides (e.g., serializer vs parser) by feeding real output into the real counterpart, without duplicating either schema. Confidence: 0.9
- Clean up temporary test resources in `try/finally`, and report cleanup failures separately without masking the original test result. Never delete resources you did not create. Confidence: 0.9
- Test errors should carry a specific, safe reason code (e.g., INVALID_PROTOCOL, INVALID_JSON) distinguishing failure types rather than one generic message. Confidence: 0.8
- Centralize shared constants/protocol definitions (protocol versions, allowed methods, canonical field names) in one place instead of duplicating magic strings across files. Confidence: 0.85
- Avoid silent fallback behavior that defeats an explicit design choice (e.g., a selected worker silently falling back to direct fetch); fail explicitly instead. Confidence: 0.9
- Provide compact PASS/FAIL test output and final reports; document exact commands to run and their results. Confidence: 0.75
- Design delete/deprovision/cleanup operations to be idempotent: treat an already-absent remote resource (404 / provider "not found") as success, and never permanently trap a row that has no remote identity (dummy/test/failed rows delete without a provider call). Confidence: 0.9
- Destructive admin operations (e.g., force-delete) must require an explicit user confirmation, be never-automatic (a separate endpoint/flow, never reached via fallback), and be audited with a warning about consequences (e.g., remote resource may remain). Confidence: 0.9
- Reuse existing generic architecture and validation logic (transports, resolvers, worker validation) instead of creating provider-specific duplicates (e.g., a second probe fetcher) or re-doing provider validation in the backend. Confidence: 0.9
- Use structured correlation-ID logs with step/status/result/route fields and target/probe context; keep values developer-comprehensible while never logging secrets, URLs, or query strings. Confidence: 0.85
- Keep fixes scoped: do not modify unrelated features or out-of-scope behavior when addressing a specific issue. Confidence: 0.9
- Apply SSRF enforcement at the layer that performs the connection: the relay edge enforces host→IP-space for relayed requests while the backend still validates URL syntax/policy (so relay mode must not require the backend to resolve targets it never connects to). Confidence: 0.85
- When a remote/file lacks an extension, append one ONLY from a known-safe Content-Type mapping; never guess for unknown types (e.g. `application/octet-stream`), never overwrite an explicit extension the user/server gave, and never produce duplicate extensions (`movie.mp4.mp4`). Confidence: 0.9
- Apply name/validation safety nets at the final authoritative layer (e.g. create/service) as well as at detection, because the earlier probe/detection result may be stale or re-derived — the creation path is the last word. Confidence: 0.85
- Detect and fix bugs by tracing the actual data-flow end to end before touching code, then confirm the exact loss path with targeted tests before/after the fix. Confidence: 0.8
- Detect provider-specific failures from the provider's error envelope (codes/messages, e.g. Cloudflare "script not found" or dependency-blocked) rather than the HTTP status alone; apply provider-specific remedies (e.g. `force=true` retry) only for the matching error class, never unconditionally. Confidence: 0.85
- Validate the user-selected resource (e.g. the chosen worker: exists/enabled/usable/driver registered) before generic URL/DNS validation, so the most specific, actionable error surfaces first and no network request is issued before the selected route is validated. Confidence: 0.8
- Expects an explicit test matrix for every fix covering success, error, edge-case, and bulk/repeated scenarios for each acceptance criterion — tests are a first-class deliverable, not an afterthought. Confidence: 0.75
- Use distinct error codes for distinct failure classes (e.g. relay-unhealthy vs upstream fetch failed) and reserve a generic "unhealthy"/"unreachable" classification only for when the infrastructure itself (relay/service) is the problem, never for a downstream/source fetch failure. Confidence: 0.85
- Retry policy for idempotent operations (GET/HEAD): bounded exponential backoff + jitter on explicit transient statuses (502/503/504) and network exceptions only; never blindly retry 4xx (400/401/403/404); retries must preserve the exact same request context (same worker/target/Range/headers); no silent fallback. Confidence: 0.85
- Preserve request-context headers (Range, User-Agent, Referer, Origin, Cookie, allowlisted context) consistently across every stage of a multi-step operation (e.g. probe, download, segments) so upstream requests are identical between the first and subsequent calls. Confidence: 0.8
- Verify zero production-source coupling to any read-only/reference folder before declaring a phase or task complete: grep imports/requires/build paths across extension, backend, and frontend source and config; confirm the folder stays unmodified and that deleting it does not break builds or tests. Confidence: 0.9
- For forensics / root-cause fixes, produce per-case debug summaries showing which candidate won and why (selectedSource, selectedFilename, relevant safe fields) — do not simply report "fixed"; the trace must explain the selection logic. Safe fields only: never URLs, cookies, Authorization, signed query values, or tokens. Confidence: 0.85
- During a new project / "Master Session" onboarding, deliver a concise 2-paragraph architecture summary (tech stack, modules, data flow, security posture) plus exactly 3 knowledge-gap questions before writing any feature code. The briefing is a first-class deliverable, not preamble. Confidence: 0.85
- Long, multi-phase work should ship a consolidated analysis document under `docs/` (audit + reverse-engineering + gap analysis in one place) as a phase deliverable, not a series of ephemeral chat messages. Confidence: 0.8
- Syntax-validate changed service-worker / extension JS files with `node --check` before rebuilding the extension zip — a quick static parse catches misplaced-listener/dangling-token bugs (e.g. stray `, ['responseHeaders'], )`) that would otherwise surface only as `Service worker registration failed. Status code: 15` at runtime. Confidence: 0.8
