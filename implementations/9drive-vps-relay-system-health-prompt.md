# 9Drive — Virtual Private Server Relay: System Health & Setup Diagnostics

## Context

The 9Drive **Virtual Private Server** relay provider was implemented in a previous task and is intended to run on a small VPS (approximately 1 vCPU / 1 GiB RAM) behind an HTTPS reverse proxy, commonly deployed by uploading a ZIP containing a Dockerfile.

**This task is a focused follow-up.** Add an easy-to-open **System Health** JSON page to the deployed VPS relay, so the operator can tell which public endpoint is configured, whether `RELAY_SECRET` exists, whether the relay is ready, and which configuration steps remain incomplete.

**Do not rebuild the relay or change the Remote Import business logic.** Inspect the implementation generated by the previous task first; reuse its runtime, routing, HMAC protocol, environment conventions, packaging, and deployment approach. Read repository instructions such as `AGENTS.md` where applicable.

## User-facing behavior

Add a browser-accessible endpoint:

`GET /system-health`

It must return **well-formatted JSON** (`Content-Type: application/json; charset=utf-8`) that can be read directly by visiting `https://<configured-relay-domain>/system-health` in a browser.

It must be accessible **without HMAC**, because its purpose includes diagnosing whether HMAC authentication has been configured yet. For this reason, strictly limit the response to an allowlisted collection of **non-sensitive setup status values**. Never include a secret, hash, fingerprint, truncated secret, other environment variable values, bearer token, signed URL, internal IP, stack trace, or user file URL. Do not add a general environment-variable viewer.

Suggested response schema (adjust field names to match existing project conventions; preserve the semantics):

```json
{
  "service": "9drive-vps-relay",
  "provider": "Virtual Private Server",
  "protocol": "9drive-relay-v1",
  "status": "ready",
  "timestamp": "2026-10-14T01:00:00.000Z",
  "uptimeSeconds": 123,
  "publicBaseUrl": "https://relay.example.com",
  "endpoints": {
    "health": "/system-health",
    "relay": "/actual-existing-relay-path"
  },
  "setup": {
    "relaySecret": { "configured": true },
    "authentication": { "mode": "hmac", "configured": true },
    "httpServer": { "listening": true },
    "relayHandler": { "registered": true }
  },
  "capabilities": {
    "rangeRequests": "implemented",
    "responseStreaming": "implemented"
  },
  "warnings": [],
  "message": "Relay service is configured. Use the authenticated connection test in 9Drive to verify that both sides share the same secret."
}
```

This is an **illustrative shape**, not permission to hardcode values. Determine all possible values at runtime from the actual application. Only report capabilities that are truly implemented. Use the actual existing relay route; do not invent a new relay request path. If an accurate public URL is not configured, return `null` and a safe warning instead of synthesizing an unverified hostname.

## URL and status semantics

- Prefer an explicit, optional, validated environment variable such as `RELAY_PUBLIC_URL` (or reuse an existing equivalent) for `publicBaseUrl`.
- Validate that the configured URL is an HTTPS URL with no embedded credentials, query string, or fragment. Never reflect arbitrary `Host`, `X-Forwarded-Host`, `Forwarded`, or other attacker-controlled request headers as an asserted public URL.
- Do **not** infer externally working HTTPS merely because the HTTP listener is running behind a reverse proxy.
- Distinguish `ready`, `not_configured`, and `degraded` (or equivalent documented states). `ready` means necessary local configuration and handlers are present, **not** that the source website is reachable or that the 9Drive-side secret matches.
- `RELAY_SECRET` presence must be a boolean only. A non-empty value is not proof of an adequately random secret; do not falsely claim secure entropy.
- Do not imply that an HMAC request has been verified merely because `RELAY_SECRET` is set.
- Return HTTP **200** for a locally ready service and **503** for an unready service. Prevent intermediaries from caching sensitive/stale status: `Cache-Control: no-store`.
- Optionally preserve the existing lightweight `/health` or `/ready` endpoint for health probes; do not break orchestration, Docker health checks, or reverse-proxy checks.

## Startup when RELAY_SECRET is missing

The operator must be able to diagnose a missing `RELAY_SECRET` safely.

If the current relay exits before serving HTTP when `RELAY_SECRET` is absent, evaluate whether a **diagnostics-only startup mode** can be introduced safely:

- It may expose only the minimal `/system-health` (and existing liveness) routes.
- It must report `status: "not_configured"`, `setup.relaySecret.configured: false`, and HTTP 503.
- All relay/proxy operations MUST fail closed; there must be no unauthenticated fetch capability, permissive fallback, or open-proxy mode.
- If a diagnostics-only mode would conflict with existing startup contracts or introduce meaningful risk, preserve secure fail-fast startup and clearly document that health cannot be reached when the process is stopped, including how to inspect the missing-secret error in container logs. Explain this tradeoff in the final report.

## Diagnostics scope

Show a minimal, operator-useful checklist using booleans or enums only, such as:

- Relay handler registered.
- HMAC mode configured.
- `RELAY_SECRET` configured.
- HTTP server listening.
- Public URL configured (not necessarily externally reachable).
- Range and streaming **support declared by the code** (not tested against an external source).
- Configuration warning messages that mention missing *variable names* only, never their values.

Do not execute arbitrary network fetches when the health page loads. Do not expose an upstream test URL or allow client-supplied destinations on health routes. Network tests must remain explicit and authenticated via the existing 9Drive connection-test mechanism. Never return user file details.

If the existing 9Drive worker settings already have a suitable place for it, optionally add a simple **“Open System Health”** link for the Virtual Private Server provider, pointing to the configured base URL plus `/system-health`. Use only operator-controlled, validated configuration. This UI link is secondary: the standalone health JSON endpoint is mandatory. Do not create a new management subsystem.

## Security and compatibility invariants

- Keep the provider's visible name exactly **Virtual Private Server**.
- Preserve `9drive-relay-v1`, HMAC verification, signing rules, replay protections, and any configured request allowlists.
- Do not leak `RELAY_SECRET`, secrets from environment variables, URL query tokens, cookies, credentials, internal hosts/IP addresses, stack traces, raw exception messages, or file URLs.
- `/system-health` must never be able to proxy content or accept a user-specified upstream destination.
- Never introduce Direct fallback or automatic switching to Cloudflare/Deno/another provider.
- Preserve existing HTTP Range, 206/404/416 statuses, streaming, backpressure, concurrency control, timeout behavior, SSRF protection, and relay error classification.
- Keep the Dockerfile, ZIP upload deploy workflow, configured port, and reverse-proxy compatibility working on a ~1 vCPU / 1 GiB VPS.
- Avoid unrelated changes to other 9Drive modules, database schema, and Remote Import user flows.

## Tests

Add focused tests for:

1. `GET /system-health` returns syntactically valid JSON, stable documented schema, and `Cache-Control: no-store`.
2. Proper `Content-Type`, HTTP 200 when locally ready.
3. Missing `RELAY_SECRET` produces a truthful unready state and HTTP 503 if the service supports diagnostic-only startup (otherwise tests/documentation prove secure fail-fast).
4. No authentication secrets, secret fragments/hashes, unrelated environment values, full signed URLs, file URLs, or internal IPs appear in response bodies or logs.
5. Untrusted forwarded-host/host headers cannot control the reported public URL.
6. Missing or invalid optional public URL gives `null` and safe warning, not an invented URL.
7. A configured relay secret does not automatically mark external connectivity or 9Drive-to-VPS HMAC compatibility as verified.
8. GET system-health and health checks cannot initiate a proxy fetch.
9. Existing authenticated relay requests, streaming, Range, and relevant HTTP statuses behave unchanged.
10. Existing container healthcheck and Docker ZIP packaging still work.
