# Stage 2 — Detect Browser Downloads and Import into 9Drive

## Prerequisite

Stage 1 — Server Browser MVP — must already be implemented.

Inspect the current implementation and extend it incrementally. Do not recreate the browser service or replace Stage 1 architecture.

## Objective

Allow users to discover downloadable resources from their own Server Browser session and import a selected resource into 9Drive using the existing Remote Import and provider-upload infrastructure.

The workflow should be:

1. User visits a website in Server Browser.
2. 9Drive detects candidate downloadable resources associated with that browser session.
3. A list of candidates appears in the 9Drive UI.
4. The user selects a candidate and clicks **Import to 9Drive**.
5. The existing import workflow handles the job, progress, completion, and errors.

This stage captures candidates and integrates imports. It does not implement browser-to-disk fallback downloads; those belong to Stage 3.

## Read First — Focused Inspection

Read `AGENTS.md` and the relevant documentation index. Inspect only:
- Stage 1 session creation and browser-service integration.
- Existing Remote Import request, queue, and status flow.
- Existing request-context validation and encryption.
- Existing provider upload and destination-selection abstractions.
- Current browser-capture implementation, if applicable.
- Focused tests in those paths.

Do not scan the entire repository or refactor unrelated code.

Before changes, trace how an existing Remote Import enters the queue and reaches the provider upload stage. Reuse that flow.

## Requirements

### 1. Capture browser requests privately

Use a supported browser automation or Chromium DevTools Protocol integration to observe requests from each isolated browser session.

Requirements:
- Associate every captured request with its owning 9Drive user and browser session.
- Keep DevTools Protocol accessible only on the private browser-service network.
- Never expose the DevTools endpoint to the public internet or the frontend.
- Do not capture requests from another user's session.
- Bound request history and remove temporary state when the session expires.
- Do not enable unnecessary browser permissions or install an unrestricted extension simply to capture requests.

Use actual request/response events rather than guessing resources from page text alone.

### 2. Detect candidate downloads

Use available evidence, including:
- `Content-Disposition`.
- Response `Content-Type`.
- Successful media or file responses.
- Plausible downloadable resource URLs and filenames.
- Relevant content-length or range metadata, when available.

Do not treat every request as a file. Exclude routine page resources such as ordinary scripts, stylesheets, fonts, tracking requests, and tiny page assets unless there is credible evidence of a downloadable resource.

Do not assume file extensions are authoritative. Some valid downloads use opaque CDN URLs or no extension.

Each candidate should have an opaque ID, a sanitized display filename when available, a useful type/size/status summary, and an association with the correct browser session. Avoid leaking full sensitive URLs in ordinary logs or UI surfaces where they are not necessary.

Allow the user to refresh or dismiss the candidate list.

### 3. Integrate with existing Remote Import

When the user selects a candidate:
- Verify the browser session belongs to the current authenticated user.
- Resolve the candidate from server-side session state; do not trust a submitted arbitrary URL or another user's candidate ID.
- Reuse the existing Remote Import job, queue, provider connector, destination selection, progress, retry, and error-handling mechanisms.
- Avoid implementing a second provider uploader.
- Prevent accidental duplicate imports where compatible with existing idempotency behavior.

The feature must preserve the candidate's actual request context where required to access the resource.

### 4. Request context and cookies

Preserve only approved headers that are genuinely needed for the selected resource request.

Use an explicit, case-insensitive allowlist. Follow the project's established request-context validation and encryption design.

Security requirements:
- Never expose raw Cookie headers, browser cookie values, or credentials to the frontend.
- Never store sensitive request context in plaintext.
- Scope cookies and sensitive headers to the exact allowed source origin.
- Revalidate redirects and strip sensitive context when the destination origin changes according to the existing policy.
- Do not forward arbitrary browser headers.
- Do not permit captured `Range` to override the Range generated by the importer for a probe or individual download operation.
- Preserve SSRF safeguards.
- Do not read the browser's entire cookie jar when a narrower request-scoped context is sufficient.

If the current architecture cannot safely pass the necessary context, explain the gap and make the smallest compatible extension.

### 5. Treat Direct and Cloudflare relay as distinct paths

Current diagnostic evidence shows Direct fetch returning HTTP 206 while the Cloudflare Worker route returns HTTP 404 for the same source.

Do not assume this issue is resolved by Stage 2.

Inspect the existing routing abstraction and implement a feature-level route choice that uses a supported, explicit Remote Import path. Where the architecture permits it, allow this browser-session import to select Direct fetch without changing global provider routing or silently changing behavior for unrelated imports.

Never misrepresent a Worker 404 as success. Preserve the actual upstream status and failure information.

Do not create a TrafficDeposit-specific workaround or hardcode a particular hostname.

### 6. UI behavior

Add a **Detected Downloads** panel associated with the active browser session.

Display loading and empty states. For each candidate, show:
- A safe filename or URL-derived display label.
- Type or content type when known.
- Size when known.
- Candidate state.
- An **Import to 9Drive** action.

Show job progress and errors through the existing import UI or job-status pattern. Avoid creating a separate job-state system if the project already has one.

### 7. Limits and cleanup

Limit captured request count, retained history, candidate count, and session lifetime. Do not retain sensitive request metadata longer than necessary.

Recheck authorization on every list, detail, dismiss, and import operation.

## Tests

Add focused tests for:
1. Candidates are isolated by user and browser session.
2. Only plausible download candidates are displayed.
3. Opaque CDN URLs can be represented without inventing filenames or extensions.
4. Candidate IDs cannot be used to import another user's resources.
5. Request headers are allowlisted and validated.
6. Sensitive request context uses the existing encrypted-storage mechanism.
7. Cookie and redirect policies remain intact.
8. Import invokes the existing queue and uploader.
9. A Worker 404 is not reported as successful import.
10. Existing Remote Import operations still work.
11. Candidate history is bounded and cleaned up.

Use mocked browser events and upstream responses where possible. Do not rely on a live third-party website for deterministic tests.

## Non-Goals

- Do not download files into a server-side temporary folder as a fallback in this stage.
- Do not rebuild provider uploads or destination selection.
- Do not change global routing or queue semantics.
- Do not expose browser credentials or unrestricted DevTools access.
- Do not refactor unrelated code.

## Definition of Done

A user can browse a site, see relevant download candidates from their own remote-browser session, and submit a selected candidate into the existing 9Drive import workflow with appropriate context and security checks.

## Final Report

Summarize request-capture architecture, UI/API changes, import integration, security boundaries, route choice behavior, test results, and any limitations.
